3. RED FLAGS - WHAT THE README DOES NOT TELL YOU     [entry 2026-08-28]
================================================================================

The README advertises "employer, job title, location, publication date,
source URL, seniority, occupation classifications, extracted skills and
metadata". Technically true. Practically misleading. Measured reality:

3.1 [VERIFIED] THERE IS NO JOB DESCRIPTION TEXT. AT ALL.
    description_derived is NULL in 70,584 of 70,584 rows (100%).
    n_unique = 0.

    Consequence: every plan of the form "let the LLM read the job ad and
    extract tech stack / project context / pain points" is DEAD on this
    dataset. The only free text we have is the job TITLE (mean 48 chars).
    Most teams will discover this hours in. We know it now.

3.2 [VERIFIED] THE ESCO OCCUPATION LABELS ARE FREQUENTLY WRONG.
    Row-level examples straight from the file:
      "Gesundheits- und Pflegeassistent/in - GPA"  -> esco: "auditing clerk"
      "Betreuungskraft / Alltagsbegleiter/in"      -> esco: "furniture
                                                      specialised seller"
      "Fullstack Developer (m/w/d)"                -> esco: "rubber goods
                                                      assembler"
      "Junior Java Entwickler (m/w/d)"             -> esco: "youth worker"
      "DevOps Engineer (m/w/d)"                    -> esco: "knitting machine
                                                      supervisor"
    In aggregate the ESCO distribution looks plausible (top labels:
    healthcare assistant 2,408; electrical engineering technician 2,117;
    software developer 747) - which is exactly what makes it dangerous.
    It is wrong per row while looking sane in aggregate.

3.3 [VERIFIED] esco_skills LOOKS SYNTHETIC.
    70,574 of 70,584 rows carry EXACTLY 5 skills (max 5, mean 4.98).
    A real skill-extraction pipeline does not return exactly five skills for
    99.99% of documents. This is a fixed top-5 from some automated tagger,
    and 3.2 shows the tagger is unreliable.
    => Do not build the scoring on esco_skills. If we use them at all it is
       as weak, aggregated evidence only, never as a row-level fact shown
       to a user.

3.4 [VERIFIED] THE GERMAN OCCUPATION CODE (kldb_2010) IS ALSO UNRELIABLE.
    KldB section 43 = "Informatik-, IKT-Berufe" (the IT section).
    Present subcodes: 431 (4,670), 433 (1,518), 432 (948). Total 7,136.
    Subcode 434 - "Softwareentwicklung und Programmierung" - is ABSENT
    ENTIRELY. The single most relevant IT code for us does not appear.

    Cross-checking KldB against a keyword read of the title:
                          title looks IT   title looks non-IT
        kldb 43                  4,711              2,425
        not kldb 43              2,191             61,257

    - 34% of "IT" KldB rows have non-IT titles
      (e.g. "Kaufmaennischer Mitarbeiter", "Projekteinkaeufer",
       "Leitende Rezeptionskraft / Front Office-Manager" are all coded 43).
    - 32% of IT-looking titles are NOT coded 43
      (e.g. "Junior Java Entwickler" is coded 83113, "Fullstack Developer"
       25112).
    CAVEAT: our title keyword rule is itself a heuristic, so both figures are
    approximate. But cases like a Java developer coded as a youth worker are
    not borderline.

    CORRECTION 2026-08-28 (second pass): the first two versions of this test
    were both wrong.
      v1 used the pattern "it " which also matches "Arbeit ".
      v2 used "\bit\b" - and DUCKDB'S REGEX ENGINE (RE2) SILENTLY IGNORES \b.
         "\bsap\b" matches 0 rows; "sap" matches 525. Every \b alternative in
         the filter never fired, so v2 undercounted IT postings.
    Numbers above are v3, matching against a space-padded token string:
         ' '||regexp_replace(lower(title),'[^a-z0-9aeoeuess#+]+',' ','g')||' '
    NEVER USE \b ANYWHERE IN THIS CODEBASE.

3.5 [VERIFIED] seniority AND salary ARE EFFECTIVELY EMPTY.
    seniority: unknown 62,088 (88.0%), entry 5,149, senior 1,773, lead 901,
               junior 672, mid 1.
               A field where "mid" has exactly ONE row is not a real field.
    salary_range: NULL in 69,330 of 70,584 (98.2%). Only 952 rows have a
               min_eur. Unusable as a signal; usable only as a rare bonus fact.

3.6 [INFERRED, high confidence] SURVIVORSHIP BIAS IN THE TIME AXIS.
    Because this is a one-night snapshot of CURRENTLY OPEN postings (2.3),
    a count of postings by posted_date is NOT a hiring-volume time series.
    Old months only contain the postings that are STILL UNFILLED today.
    Everything filled or expired has vanished from the data.

    So the naive stretch goal "hiring velocity / acceleration" computed as
    postings-per-month from this file is WRONG, and will look right. Any team
    that plots that curve is plotting a decay function of vacancy survival,
    not hiring demand.

    The flip side is our biggest opportunity: if a posting is still open,
    that vacancy is UNFILLED. Age of an open vacancy is a direct, defensible
    measure of unmet hiring demand - which is precisely the pain that a
    nearshore delivery partner solves. See section 5.

5. DESIGN IMPLICATIONS                  [entry 2026-08-28]
================================================================================

Derived from sections 1-4. Not yet decided - input for the design session.

5.1 The signal that the data actually supports
    Because we have a snapshot of open vacancies with publication dates, the
    strongest defensible measure is UNMET DEMAND, not hiring volume:
      - how many IT vacancies a company has open RIGHT NOW
      - how many have been open past 90 / 180 days
      - how CONCENTRATED they are in one skill

    CORRECTION 2026-08-28: two claims in the first version of this section
    were tested and FAILED. Recording both, because both are traps.

    (a) "Vacancy age = unmet demand" IS FALSE ON ITS OWN.
        Ranking companies by median vacancy age returns: alfatraining
        (a training school, 481d), Computacenter (473d), avivar experts,
        BridgingIT, inovex, PPI AG, 360 Consulting, CANCOM, Deloitte (304d).
        These are IT consultancies running EVERGREEN "always hiring" ads -
        LITIT's competitors, not its customers. Age alone selects for exactly
        the wrong companies.
        => Age is only meaningful AFTER company classification. This is why
           the algorithm is a cascade: the gate must precede the score.

    (b) MEDIAN age is the wrong statistic even inside the eligible pool.
        A company posting many fresh ads shows a low median regardless of how
        hard its roles are to fill. Median age measures POSTING CADENCE, not
        difficulty. Use COUNT of vacancies still open past 90/180 days - a
        direct observation that survives the confound. Median age is retained
        for display only.

    (c) MARKET SCARCITY per tech family is NOT measurable from one snapshot.
        Median vacancy age by family: SAP 14d (lowest), web 30d (highest).
        That does not mean SAP is easy to fill - it means SAP ads are posted
        more recently and churn faster. One snapshot cannot separate "posted
        recently" from "filled quickly"; that needs two snapshots and a
        duration model. Dropped from scoring, kept as context.
        => A SECOND SNAPSHOT from the live BA API would make this properly
           measurable. Highest-value upgrade available to us.

5.2 Things we must NOT do
      - do not rank by count (3.7 proves what that returns)
      - do not compute month-over-month "velocity" from posted_date (3.6)
      - do not surface esco_skills as facts to the user (3.2, 3.3)
      - do not let an LLM invent a signal; the LLM phrases numbers we
        computed, it never sources them

5.3 Things that will differentiate us with judges
      - the "naive ranking vs our ranking" side-by-side (3.7)
      - filtering out intermediaries, and being able to explain how
      - catching our own parent company in the results
      - stating the survivorship-bias trap out loud (3.6) - it demonstrates
        data judgement, and it is a free "limitations" slide the README
        explicitly asks for
      - every claim clicking through to a real arbeitsagentur.de URL

5.4 Open design questions -> section 7

6. PRIOR ART AND EXTERNAL RESOURCES     [entry 2026-08-28]
================================================================================

6.1 LIVE DATA - the same source is queryable in real time
    The dataset is a scrape of the Bundesagentur "jobsuche" API v4. That API
    is publicly documented and reachable:
      - github.com/bundesAPI/jobsuche-api  (community OpenAPI spec)
      - github.com/wunderfrucht/jobsuche   (Rust client)
      - arbeitsagentur.de hosts ~1.5M active postings [reported, unverified]
    Three things this unlocks:
      (a) the "live job acquisition" stretch goal is genuinely reachable;
      (b) the API reportedly returns the FULL description text that our
          dataset is missing (3.1). Enriching only our top ~100 ranked
          companies would restore text signal cheaply;
      (c) the API exposes filter parameters for Zeitarbeit (temp staffing)
          and Privatvermittler (private agencies) - direct confirmation that
          intermediary contamination (3.7) is a known, named problem.
    [UNVERIFIED] We have not yet called the API or confirmed rate limits,
    auth requirements, or that description text is really returned. DO THIS.

6.2 Commercial analogues - this product category exists
    PredictLeads, Revelio Labs, LinkUp, Coresignal, Lightcast (ex-Burning
    Glass), Thinknum, JobsPikr. The accepted industry framing is "hiring as
    a buying signal": an influx of job ads implies budget movement and
    capability gaps a vendor can fill. Worth one sentence in the demo to
    show we know we are building a recognised category, not a toy.

6.3 Academic grounding for "job postings as a firm-level signal"
    - Hershbein & Kahn (2018), widely used validation that online postings
      track official occupation/industry statistics, and that firms shift
      skill requirements in response to shocks.
    - NBER w28257 "AI and Jobs: Evidence from Online Vacancies" - builds
      establishment-level AI adoption measures from vacancy skill text.
    - Lightcast/Burning Glass representativeness analyses - useful for how
      to state coverage limitations honestly.
    Value to us: one slide citing that firm-level inference from vacancy
    data is an established method lifts this above "we made up a score".

6.4 Entity resolution (needed for 3.8)
    Standard approach: strip legal forms (GmbH, AG, SE, KG, GmbH & Co. KG,
    e.K., mbH, oHG), normalise umlauts, casefold, then fuzzy match.
    Known trap: tokens like Group, Holding, Services, Solutions, Deutschland
    carry real meaning and must NOT be stripped, or distinct subsidiaries
    collapse into one. Our own data shows both failure modes
    (PerZukunft = under-merged; NTT entities = genuinely different legal
    entities of one group).

6.5 Taxonomies we could use for title -> occupation
    - KldB 2010 (German official). Full 5-digit code list downloadable from
      BIBB metadata repository. We would be re-deriving codes ourselves,
      since the dataset's codes are unreliable (3.4).
    - ESCO (EU occupation/skill taxonomy). Same caveat.
    [UNKNOWN] Whether a taxonomy is worth the time at all, versus a curated
    keyword/tech-stack dictionary built for the IT segment only. The second
    is smaller, faster, fully explainable, and covers the only segment we
    care about. Leaning that way.
