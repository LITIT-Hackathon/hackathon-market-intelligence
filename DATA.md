# OpRadar — Data Dictionary

**v1, 2026-08-29.** What every column is, and — the important part — whether
it was measured or invented.

## The one rule

**A column named `sim_*` is invented. Everything else came from the German
posting data.**

That prefix is the whole safety mechanism. It survives joins, it shows up in
the UI, and it means nobody has to remember which fields are real. If a number
goes on a slide, check the prefix first.

Generated by `python -m opradar.simulate`. Seeded (`SEED = 20260829`), so two
runs produce identical files — a fixture that drifts is worse than none, because
you cannot tell a real ranking change from generator noise.

---

## Why simulate at all

Six sources would materially improve this product. None are integrated, by
choice — this is a self-contained test set, not a set of live dependencies.

| what we want | real source it stands in for | why not now |
|---|---|---|
| vacancy timelines, time-to-fill | a second and third BA API crawl | needs elapsed time we don't have |
| salary by region and seniority | Bundesagentur Entgeltatlas | OAuth API, extra dependency |
| company size, revenue | Handelsregister / Bundesanzeiger | terms restrict bulk republishing |
| public IT programmes | TED procurement notices | separate integration |
| engineering footprint | GitHub API | see the note below |
| headcount growth | LinkedIn | scraping breaches ToS, and GDPR |

Every simulated field is generated from hand-set coefficients in
`opradar/simcoeff.py`, each block naming the source it replaces. Swapping
simulation for reality later means deleting one function, not unpicking the
pipeline.

### The GitHub decision

GitHub signal is simulated **onto people, not companies** — deliberately.

Our ranked companies are Deichmann, Fressnapf, DKV Euro Service, JobRad,
Hamburger Energienetze, 50Hertz, ING, LBBW. Shoe retail, pet retail, fuel
cards, bike leasing, energy grids, banks. Perhaps two of the top eighteen have
a meaningful public GitHub org, and BMW's tells you nothing about whether they
need SAP contractors.

Worse, a public GitHub presence is strongest at exactly the software houses
and consultancies the classifier **excludes as competitors**. Company-level
GitHub is high effort, low coverage, and aimed at the wrong segment.

For an individual consultant it is a genuine competence signal, so that is
where it lives.

## `postings_sim.parquet` — one row per job ad (70,543)

Inherits every column from `postings.parquet`, plus:

| column | real? | meaning |
|---|---|---|
| `sim_market_salary_eur` | simulated | what a German employer pays for this role, in this region, per year |
| `sim_expected_fill_days` | simulated | how long this kind of role normally takes to fill |
| `sim_filled` / `sim_still_open` | simulated | outcome, as a second crawl would have revealed |
| `sim_time_to_fill_days` | simulated | actual days taken, null while still open |
| `sim_filled_on` | simulated | date the role left the board |
| `sim_repost_count` | simulated | times an unfilled role was re-advertised |
| `sim_overdue_days` | simulated | days open beyond what this role normally takes |
| `project_id` | **real** | programme this posting belongs to (§ projects) |

**Salary** = seniority base × regional index × technology premium.
Base: junior €48k, mid €62k, senior €80k, lead €98k. Regional index runs
Bayern 1.12 down to Sachsen-Anhalt 0.82. SAP carries +14%, support −10%.
Observed output: lead €106k, senior €85k, junior €50k; Bayern €93k vs
Bremen €77k for the same senior role.

**Lifecycle** draws an expected fill time from seniority, technology scarcity,
regional tightness and employer size, then compares it to how long the ad has
actually been open. Observed: lead 117 days expected vs junior 41, and 85% of
lead roles still open against 65% of junior. That skew is the real-world
survivorship effect — hard roles are over-represented among the ads you can
still see — and reproducing it is the point.

`sim_overdue_days` is the honest version of "unfilled demand": open *longer
than this kind of role should take*, rather than open longer than an arbitrary
45 or 90 days.

## `companies_sim.parquet` — one row per company (18,416)

Inherits `companies.parquet`, plus:

| column | real? | meaning |
|---|---|---|
| `industry` | **real** | inferred from the company's own non-IT postings |
| `sim_employees` | simulated | headcount |
| `sim_revenue_eur` | simulated | annual revenue |
| `sim_founded_year` | simulated | year founded |
| `sim_has_tender` / `sim_tender_ref` / `sim_tender_value_eur` | simulated | live public IT procurement (public sector only) |
| `sim_opportunity_type` | simulated | see below |
| `sim_urgency` | simulated | 0–1, how open the window is |
| `sim_act_within_days` / `sim_act_label` | simulated | "this week" … "no rush" |
| `sim_open_roles_salary_eur` | simulated | combined salary of everything they cannot fill |
| `sim_median_time_to_fill` | simulated | their own hiring speed |

**Industry is real and free.** A company advertising nurses is in healthcare;
one advertising Netzmonteure is in energy. Firmographic signal the dataset
already contained, from the non-IT postings we otherwise discard.

**Opportunity types** — observed counts:

| type | n | meaning | urgency |
|---|---|---|---|
| `new_entry` | 845 | small and hiring now — just started building | 0.62 |
| `stuck` | 614 | most roles overdue — cannot fill what it advertised | 0.07 |
| `low_demand` | 384 | quiet, mostly old ads | 0.24 |
| `replacement` | 87 | routine backfill | 0.59 |
| `scaling` | 36 | high volume and hiring fast | 0.72 |
| `transformation` | 27 | a multi-role programme is running | 0.78 |

**`stuck` scoring lowest urgency is deliberate and worth defending on stage.**
A company that has been failing to hire for six months is not a fresh
opportunity — it is already talking to three of your competitors. The window
is widest when a programme has just opened, which is why `transformation` and
`scaling` rank highest.

`sim_open_roles_salary_eur` is the sales argument in one number: what the
unfilled roles would cost to staff locally.

## `projects.parquet` — detected programmes (30)

**Not simulated.** Genuine co-occurrence over real postings.

A cluster of roles is a programme when one company opens **3+ roles**, sharing
a **technology**, across **2+ role families**, inside **21 days**.

| company | tech | roles | families | seniors | span |
|---|---|---|---|---|---|
| Deutsche Telekom MMS | erp | 7 | 2 | 4 | 2 days |
| Deichmann SE | data | 5 | 2 | 5 | same day |
| Deutsche Telekom AG | cloud | 5 | 3 | 4 | 10 days |

Deichmann opening five senior data roles across two disciplines on one day is
a data platform programme nobody announced. That is the "hidden project"
signal, and it needed no data we did not already hold.

⚠️ **Known defect.** Detection runs over the eligible pool, which still leaks
recruiters. `KA Resources` shows 22 ERP roles in a zero-day span — that is
bulk agency posting, not a programme. Project detection needs the same
classification gate as the ranking, and currently lacks it. Filter on
`company_class` before quoting any of these.

## `bench_sim.parquet` — one row per consultant (120)

Inherits `bench.parquet` (already synthetic — labelled `source='synthetic'`),
plus:

| column | meaning |
|---|---|
| `sim_github_profile` | has a public profile at all |
| `sim_github_repos` / `sim_github_contributions_12m` / `sim_github_stars` | activity |
| `sim_day_rate_eur` | nearshore day rate charged to a German client |
| `sim_notice_days` | lead time before they can start |
| `sim_utilisation` | share of the last year billed |
| `sim_client_rating` | internal delivery rating, 3.2–5.0 |
| `sim_certifications` | held certifications, drawn from their tech tags |

Observed GitHub distribution — the realism check that matters:

| family | with a profile | median contributions |
|---|---|---|
| dev | 77% | 307 |
| ops | 62% | 46 |
| data | 55% | 25 |
| qa | 42% | 0 |
| analyst | 10% | 0 |
| support | 14% | 0 |

Stars are drawn very heavy-tailed: most consultants have almost none, a few
have hundreds. That is how GitHub actually looks, and a uniform draw would
make the field useless as a discriminator.

Day rates: junior €385 → mid €514 → senior €679 → lead €823, with roughly a
9% premium where the consultant speaks German — capability that is genuinely
chargeable and unlocks work others cannot take.

## Honest limitations

1. **None of the `sim_*` columns are evidence.** They are shaped like reality,
   not drawn from it. Never put a simulated figure on a slide without saying so.
2. **Correlations are the ones we imposed.** Senior roles take longer to fill
   here because we made them; it is a plausible assumption, not a finding.
3. **Project detection leaks agencies** — see the defect above.
4. **Salary is occupation-level, not company-level.** A real Entgeltatlas pull
   would carry the same limitation.
5. **Simulated fill outcomes are consistent with observed ages by construction**,
   so they cannot be used to validate the age-based signals. That would be
   circular: the generator was told what the answer should look like.
